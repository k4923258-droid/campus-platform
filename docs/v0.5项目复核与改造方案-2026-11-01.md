## 实施前复核结论

现有代码尚不符合 v0.5。主要业务流程已经实现，缺口集中在身份核验、团队成员绑定、账号恢复与正式／演示环境隔离。邮箱验证码不能作为孤立页面添加：报名、成员解析、数据查询、附件访问、通知和退出团队必须同时改为以用户 ID 判断关联关系。

用例图表达角色与能力、包含和扩展关系；操作顺序、前置条件、异常处理和权限判定仍以用例说明与具体需求为准。不能把参与者连线当成流程顺序。

|---|---|---|
| UC-01 提交报名 | 已有表单、时间、重复报名、版本与重审逻辑 | 增加本人和全体队员的身份检查；成员改为用户 ID 关联 |
| UC-02 发布活动 | 已有组织范围、草稿发布、字段与环节配置及首条报名后的结构锁定 | 管理入口同时检查账号状态与组织授权 |
| UC-03 审核报名 | 已有评分草稿、正式确认、旧版本拒绝、停用／默认通过环节与批量操作 | 纳入 v0.5 身份与团队约束的回归；真实接口重新验收 |

## 已确认的问题

| 优先级 | 问题与影响 | 本地源码位置 |
|---|---|---|
| P0 | 旧入口仍可用自填学号、姓名和密码直接创建普通用户 | `backend/src/main/java/cn/campus/platform/ApiController.java` 的 `command`；`PlatformService.java` 的 `register`；`src/domain/engine.ts` 的 `register` |
| P0 | 团队成员只检查学号格式、人数与活动内占用，没有检查用户是否注册、核验或停用 | `Rules.java` 的 `application.save`；`src/domain/engine.ts` 同名操作 |

| P0 | 附件权限依赖报名快照，团队关联错误会影响附件可见范围 | `PlatformService.java` 的 `file` 与 `Rules.snapshot`；前端模拟快照同样需要修改 |

## 账号核验的实现

保持现有 Vue 与 Spring Boot 技术栈。当前一个业务服务即可承载认证，不另建统一认证网关。校邮核验、平台会话、业务授权和将来的学校身份提供方各自独立，最后关联到同一个平台用户 ID。

1. **先建立身份与会话模型。** 用户记录账号状态；身份记录邮箱验证时间、可信学号绑定状态和身份来源；会话记录账号的安全版本号。身份核验不产生负责人或管理员权限。对外使用明确字段清单，排除内部凭据和无关邮箱信息。
2. **把正式身份约束放进数据库。** 校邮、可信学号和外部身份标识采用独立字段和唯一约束，关联平台用户 ID。未验证申请放在临时申请表，不占正式学号。学校身份采用“提供方＋稳定标识”唯一约束，不凭显示姓名合并。
3. **校园邮箱注册。** 输入白名单校邮，申请验证码，填写验证码、平台密码和显示姓名后提交。后端验证申请、验证码、用途与可信映射，在同一事务内消费验证码、校验唯一性、创建账号并绑定身份。界面可以分步，但最终以服务端结果为准。映射未确认时保留待核验状态，正式报名和团队数据入口关闭。
4. **验证码服务。** 按文档使用安全随机 6 位数字、5 分钟有效、同一申请最多失败 5 次、60 秒重发间隔、成功重发使旧码失效。验证码绑定申请、邮箱及用途。考虑到 6 位数字空间很小，保存带服务端密钥的摘要，不将可用验证码直接入库或写日志。失败次数须可靠落库，不能因抛出业务异常而随事务回滚。
5. **找回密码与换绑。** 注册、恢复和换绑使用各自用途的申请，不能互用。恢复成功使账号全部既有会话失效，用户重新登录。换绑须重新认证、验证新地址并通知原地址；原邮箱不可用时转人工核验。
6. **学校认证只做预留。** 提供认证方式查询、发起与回调入口；配置缺失时明确不可用，不能建立“学校已认证”状态。取得正式协议后再实现适配器、可信字段映射、请求关联、重放校验和回调联调。

密码方案须满足文档的 8～128 字符和不截断要求。当前服务使用 BCrypt，应核对其 72 字节输入限制；新正式账号建议采用 Argon2id，避免直接把“字符数校验通过”等同于散列算法能处理完整密码。演示引擎的 SHA-256 不进入正式认证服务。

接口先落实文档中的 `/auth/email/challenges`、`/auth/register`、`/auth/password/reset`、`/auth/providers`、学校认证预留入口和 `/session`。旧 `/commands/register` 不能保留免验证路径。补验证、换绑和身份冲突处理还需在实施任务中明确接口与权限，不能只做前端入口。

## 团队规则的实现

继续执行“队长添加即时生效、全员通知、成员可以自行退出”，不增加逐人确认。

1. 队长按完整学号查询可加入的已核验账号。接口要求登录、活动范围和调用频率检查，只返回必要的用户 ID、显示姓名及可加入状态，不返回全量用户目录、邮箱或联系方式。
2. 报名请求提交成员用户 ID。队长由当前会话确定；后端重新读取成员身份，核对可信学号、账号可用状态和人数，再检查活动内占用。前端传来的“已核验”状态不参与授权。
3. 成员关系保存用户 ID；学号保留为可信身份快照或展示值。团队详情、附件读取、站内信收件人、编辑和退出全部按用户 ID 处理。`memberNos` 不再作为访问凭证。
4. 有效报名占用同时约束“活动＋用户 ID”和“活动＋可信学号”。入队、撤回、退出和预约变动在数据库事务内完成，失败整体回滚。
5. 队长修改成员后增加报名版本；滚动审核模式下，保留旧版本历史、使原结论失效、释放原预约并从首个启用环节重审。退出立即释放退出者占用并通知队长；低于下限时保留报名、暂停确认流转，截止仍不足时标记未通过。
6. 身份冲突或待核验账号不自动认领历史团队。旧数据迁移需要明确的管理员决定；本人验证了校邮也不能直接继承演示管理员、负责人或旧成员关系。

## 演示数据与本地邮件

- 当前数据保留在演示环境。正式身份环境使用独立数据库、文件目录和配置；创建空的正式账号体系，不把公开演示账号直接转成已核验账号。
- 本地采用 Mailpit 一类 SMTP 测试服务，邮件只进入本地收件箱。模拟校邮和本地邮件投递结果明确标记为测试，不能标记为真实校邮核验。
- 开发与自动化测试可配置测试身份映射，但该配置只能在测试环境生效。真实发件配置未就绪时，正式注册显示不可用，不回退到页面显示验证码或免验证注册。
- 发件服务切换通过后端配置完成，密钥不进入前端或仓库。校方认证仍保持独立的未启用状态。

## 需要澄清的文档表述

1. 两张用例图已经出现 UC-01～UC-14，但正文“核心用例摘要”只到 UC-09。建议为 UC-10～UC-14 增加需求和测试追踪，不必因此额外增加功能需求编号。
2. UC-09 摘要把过期、重放、用途错误与邮箱不可用一起写为“转入人工核验”；详细异常流程则将前几类拒绝，只有原邮箱不可用转人工。建议实现为验证码错误可修正或重发，邮箱不可用与身份冲突再转人工。
3. UC-08 异常说明将用户取消、网络故障、非法回调和身份冲突放在同一段并统一转管理员。建议取消与暂时故障允许重试，非法回调拒绝并记安全日志，身份冲突才进入管理员核验。
