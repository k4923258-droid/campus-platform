# 业务规则与实施约定

依据：需求文档 v0.4 与本轮已确认补充决定。原始 Word 未改动。

1. 报名时间左闭右开；服务端时间决定是否接受提交。活动公开状态与报名审核环节分开计算。统一审核截止后触发，滚动审核提交即触发。
2. 报名与审核按版本关联。评分草稿可以修改，不推进状态；正式确认绑定当前版本与环节。修改报名和队员退出后清除原审核结论、释放预约并重新审核。
3. 同一活动内学号唯一，涵盖本人、队长与队员。撤回释放整队占用；普通成员退出仅释放自己。团队少于下限时暂停人工确认流转，截止仍不足则未通过。
4. 初审、笔试、面试顺序固定。停用跳过，默认通过自动流转；100分制合格线与分数均为0—100整数。
5. 团队仅队长预约，一队占一个名额。改选必须保证原时段未开始、新时段未满，失败保留原预约。变更已有预约的时段须填写原因并通知重新选择。
6. 所有有效报名审核完成且报名截止后可以发布结果。未选中的待录取记录标为未录取。撤回须填写原因，仅恢复本次录取结果；重新发布增加结果版本。没有候补，无七天更正限制。
7. 产生首条报名后，组织、通道、团队方式、表单结构、审核环节及审核时机锁定。公告与截止时间更新通知报名者。
8. 管理权限由组织授权决定。游客快照不包含报名、私人通知或密码；负责人只能管理获授权组织；普通队员能查看团队资料但不能修改。
9. 结项后手动归档须完整输入标题确认；自动归档以结项后首个完整学期结束为界，由管理员维护学期日历。删除个人报名、相关通知、可关联个人的活动审计和不再引用的附件，只留总数。账号记录独立于报名记录，不因某活动归档删除。
10. 后端使用MySQL悲观写锁串行化业务变更，成员占用另加数据库唯一键。当前按单Java进程部署，读取使用提交后的内存投影。写入吞吐需以实际压测为准。
11. 表单、环节结果、活动配置按独立业务集合保存；后端各集合使用独立表的JSON正文，索引约束另存关系表。这是课程验证实现，尚未将每个字段拆成关系列。数据库迁移由Flyway维护。
12. 仅服务器模式能证明服务端权限、真实文件检查和数据库事务。浏览器模拟模式使用IndexedDB与命令队列，不能据此声称通过真实并发、安全、备份或性能指标。

## 归档与备份

下架活动从公开信息墙隐藏，但报名者仍可在“我的参与”查看自己的历史，避免状态变更后丢失上下文。下架活动允许负责人或管理员直接结项，随后可执行归档；继续报名、审核与预约仍被拒绝。

数据库与附件备份保留最近七份；项目独立目录中的 archive-ledger.json 保存已归档活动编号。恢复脚本保留现有清理记录，后端启动在接受请求前重新清理旧备份中的对应个人数据。旧备份可能在七份保留期内含归档前数据，不能声称存储介质上已立即不可恢复。已经由用户导出的名单无法由平台收回。

备份与归档需要在部署环境中实际检查。脚本成功不代替恢复演练，测试数据不代替真实用户反馈。
